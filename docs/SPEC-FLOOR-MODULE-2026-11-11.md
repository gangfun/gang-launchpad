## 1. 做什么

一个 3.0 V3 有税币的收款合约。税收到模块后不回购、不加池，**留在模块里当金库**。任何持有人随时可以把代币交给模块销毁，按比例取走金库里的报价币。

dev（及合作方）可以从税里拿一份，规则和封顶模块完全一样：累计拿到写死的上限后就再也拿不到，之后税全部进金库。也可以设成 dev 一分不拿。

对外可以这样说：**税收进金库，谁都动不了；任何人随时能把币按金库底价换回 BNB。**

### 底价怎么算

```
流通量   = 总供应量（10 亿，固定） − 0xdead 里的代币
金库     = 模块里的报价币 − 属于收款人的部分（欠款、已记账未推送的、新入账里他们的份额）
每枚底价 = 金库 ÷ 流通量
```

池子里的代币、税处理合约里还没卖掉的税币都算在流通量里。这样算偏保守，但流通量不随池子状态变化，无法用闪电贷操纵。

### 赎回怎么算

持有人交出 `amount` 枚：

```
应得   = amount × 金库 ÷ 流通量        （向下取整）
手续费 = 应得 × redeemFeeBps ÷ 10000   （留在金库）
到手   = 应得 − 手续费
```

交出的代币转进 0xdead。手续费留在金库里，所以每次赎回之后，剩下的人每枚底价只会更高。

### 算一笔账

买卖税 3%、分红 0、dev 比例 50%、上限 20 BNB、赎回手续费 2%。池子成交 100 BNB 时：

| 去向 | 封顶前 | 封顶后 |
|---|---|---|
| 平台（成交额的 0.5%） | 0.50 BNB | 0.50 BNB |
| 模块收到 | 2.50 BNB | 2.50 BNB |
| → 收款人 | 1.25 BNB | 0 |
| → 金库 | 1.25 BNB | 2.50 BNB |

### 底价能有多高

`底价 ÷ 市价 ≈ 进金库的比例 × 累计成交额 ÷ 市值`。进金库的比例 = `(税率 − 0.5%) × (1 − 分红比例) × (1 − payBps)`，封顶后最后一项为 1。

| 税率 | 分红 | 进金库的比例 | 累计成交额 ÷ 市值 | 底价 ÷ 市价 |
|---|---|---|---|---|
| 3% | 0% | 2.5% | 2 倍 | 5% |
| 3% | 0% | 2.5% | 8 倍 | 20% |
| 5% | 0% | 4.5% | 8 倍 | 36% |
| 3% | 40% | 1.5% | 8 倍 | 12% |

**底价通常远低于市价。** 它是暴跌时的保底，不是平时的支撑。市价跌到底价附近时，从池子买币再赎回有利可图，套利会把池子价格托在底价之上（扣掉买入税和池子手续费）。

## 2. 底价管什么、不管什么

**这一节决定对外口径，必须写进运营文档和网站。**

| 项目 | 说明 |
|---|---|
| 毕业前 | 没有底价。内盘不收税，正常情况下金库是空的；有人在毕业前直接往模块转报价币会照常拆分记账，但代币锁定，无法赎回 |
| 毕业后 | 底价从 0 起步，随外盘成交慢慢涨 |
| 每枚底价 | 以报价币计，只增不减（报价币被冻结扣减的情况除外，K-7） |
| 市价 | 不保证。市价可以远高于底价，也可以一路跌到底价附近 |
| 买入成本 | 不保证。在高于底价的价格买入，赎回一定亏损 |
| dev 持有的代币 | 不受限。dev 也可以按同样的规则赎回 |
| 曲线手续费分成 | 不受限，留在 pad 上由创建者领取 |
| 持有人分红 | 不相关，由 `dividendBps` 决定 |

网站和 CLI 不使用“保本”“只涨不跌”这类说法，只展示金库余额、每枚底价、底价与市价的比例。

## 3. 关键决定

| # | 决定 | 理由 |
|---|---|---|
| K-1 | 新写一个合约和工厂，不改封顶模块的源码 | 同封顶模块 K-1 |
| K-2 | 从封顶模块复制收款人、上限、推送、欠款、`setPayee`、`bind` 的代码；**删掉全部回购和加池的代码**（分块、TWAP、`chunk`、`previewChunk`） | 金库不换币，这些都用不上。合约比封顶模块小一半以上，没有换币就没有夹单 |
| K-3 | 上限、比例、赎回手续费、收款人、份额全部写死，谁都不能改 | 底价的价值在于规则不可改 |
| K-4 | 流通量 = `totalSupply() − balanceOf(0xdead)`，不扣除池子和任何其他地址 | 只依赖两个无法被单笔交易临时改变的数。扣除池子储备会让闪电兑换能抬高底价 |
| K-5 | 赎回的代币转进 0xdead | `GangToken` 没有销毁函数，供应量固定 10 亿。非池子转账不收税（`_shouldTax`） |
| K-6 | 金库用一个变量 `treasuryHeld` 记账（上次拆分时的金库）；`treasury()`、`floorPrice()`、`previewRedeem()` 都把还没拆分的入账按拆分规则算进去，`redeem` 先拆分再算 | 收款人的份额只对新到的钱生效，所以要记住哪些已经拆过。封顶后（或没有收款人时）新到的钱全部是金库，视图已经算上，不需要 keeper。有人直接往模块转报价币，按普通入账处理：封顶后等于捐给所有持有人 |
| K-7 | 报价币被冻结或扣减时，金库按实际余额算，底价相应下降 | 模块无法补上被扣的钱。只有 USD1 这类可冻结的报价币才可能遇到 |
| K-8 | 绑定的报价币以外的资产，全部打进 0xdead | 同封顶模块 K-8。其他资产无法计入底价 |
| K-9 | 赎回只付报价币（WBNB 报价的币付 WBNB），可以指定收款地址 `to` | 少一条原生币的出口。USDT 黑名单地址可以换一个 `to` |
| K-10 | 毕业前不能赎回，回滚 `NotTradable` | 代币锁定时本来也转不动；提前写明，免得曲线手续费被领进模块后出现半可用状态 |
| K-11 | 允许没有收款人：`payBps = 0`、`capAmount = 0`、收款人为空 | 纯底价币是最干净的卖点，见 D-2 |
| K-12 | 只部署给 GangLaunchpad 3.0 | 同封顶模块 K-12 |
| K-13 | **模块创建时就写死它服务的代币地址**，`bind` 只做校验，不能选币 | 3.0 的代币地址由 CREATE2 决定（`Pad3VanityDeployer.predict`），发币前就能算出来，而且算式里不含收款地址，所以没有循环依赖。写死之后，模块的金库只可能被这一个币的持有人赎回，诱饵币抢不走绑定（§6）。前提：abcd 地址部署器已在主网启用。2026-11-11 主网尚未启用，测试网已有，所以主网部署排在 abcd 启用之后（§7） |

## 4. 合约接口

### 工厂 `GangFloorModuleFactory`

```solidity
function create(
    address token,           // 将要发的币的地址（发币前算出），写死，见 K-13
    address floorQuote,      // 金库的计价币，也是这个币的报价币
    uint256 capAmount,       // 收款人上限；没有收款人时为 0
    uint16 payBps,           // 封顶前给收款人的比例，0–10000；为 0 时没有收款人
    uint16 redeemFeeBps,     // 赎回手续费，0–500，写死（D-1）
    address[] calldata payees,
    uint16[] calldata shares,
    bytes32 salt
) external returns (address module);
```

- 只有 Agent 能调用。克隆、初始化、`listModule(module, "floor-v1")` 在同一笔交易内完成。
- `payBps` 和 `capAmount` 必须同时为 0 或同时大于 0；为 0 时收款人数组必须为空。
- `floorQuote` 必须是 keeper 服务的报价币（同封顶模块审计 L-1）。
- 工厂要求 pad 已启用 abcd 部署器（否则 `NoVanityDeployer`），`token` 必须以 `abcd` 结尾且地址上还没有合约（否则 `BadToken`）。没有 abcd 部署器的 pad 上，代币地址取决于部署器的 nonce，任何人都能抢先占掉，dev 的币就会把税打进一个永远绑不上的模块（审计 M-1）。
- 写死的地址存在 `floorToken`。`token()` 沿用其他模块的含义：绑定前是 0，绑定后等于 `floorToken`。网站和索引照旧用 `token()` 判断是否已绑定。
- `bind(address token)` 保留 `IGangRecipientModule` 的签名，keeper 和 CLI 不用改：参数必须等于 `floorToken`（否则 `WrongToken`），并校验它已由 dev 创建、是曲线币、报价币是 `floorQuote`、税收接收地址是本模块。任何人都能调用。绑定前不拆分、不赎回。
- dev 没有在这个地址发出币（没发，或发币参数和预先计算的不一致导致地址不同）：模块绑不上。如果 dev 同时把另一个币的税收接收地址填成了它，那个币的税会停在模块里，直到 dev 按原参数发出 `floorToken` 为止；之后这笔钱按普通入账拆分。这属于 dev 或 CLI 的失误，和封顶模块“报价币填错，税留在合约里”同一类。CLI 必须在发币前模拟 `createWithSalt`，返回地址不等于 `floorToken` 就中止。

### 模块 `GangFloorModule`

实现 `IGangRecipientModule`（`moduleType` = `floor-v1`）。

| 和封顶模块相同 | 删掉 | 新增 |
|---|---|---|
| `split`、`distribute`、`release`、`setPayee`、`payeesOf`、`owedOf`、`keeperServes`、`unsplit`、`undistributed`、`capLeft`、`capReached` | `chunk`、`previewChunk`、`buybackLeft`、`lpLeft`、TWAP 相关 | `redeem`、`previewRedeem`、`treasury`、`floorSupply`、`floorPrice`、`floorToken`、`payeesPending`；`bind` 多了 `WrongToken` 和 `NothingForRecipient` 两项校验 |

```solidity
uint16 public redeemFeeBps;

/// 交出 amount 枚（需要先 approve 给模块），收到的报价币不少于 minQuoteOut，付给 to。
function redeem(uint256 amount, uint256 minQuoteOut, address to)
    external returns (uint256 quoteOut);

function previewRedeem(uint256 amount) external view returns (uint256 quoteOut, uint256 fee);
function treasury() external view returns (uint256);     // 拆分之后的金库余额
function floorSupply() external view returns (uint256);  // totalSupply − balanceOf(0xdead)
function floorPrice() external view returns (uint256);   // treasury × 1e18 ÷ floorSupply

event Redeemed(
    address indexed holder, address indexed to,
    uint256 tokensIn, uint256 quoteOut, uint256 fee,
    uint256 treasuryAfter, uint256 supplyAfter
);
error NotTradable();
error Slippage();
error ZeroAmount();
error WrongToken();       // bind 的参数不是 floorToken
error BadTo();            // to 是模块本身
error NothingToRedeem();  // 到手为 0（金库为空，或数量太小取整为 0）
error NothingForRecipient(); // bind：这个币的税全部给了持有人分红
// 工厂：
error NoVanityDeployer();  // pad 没有启用 abcd 部署器
error BadToken();          // 地址不以 abcd 结尾，或已经有合约
```

### `redeem` 的顺序

1. `nonReentrant`；`amount > 0`，`to` 非 0 且不是模块本身。
2. 已绑定且已毕业（池子已设），否则 `NotBound` / `NotTradable`。
3. 拆分但不推送：先把还没拆分的入账拆掉，收款人的份额记入上限并留在 `payeesPending`，由下一次 `split` / `work` 推送。赎回过程不调用任何收款人，收款人拒收或耗 gas 都影响不到持有人（审计 L-3）。
4. 读 `treasury` 和 `floorSupply`，算 `应得`、`手续费`、`到手`；`到手 < minQuoteOut` 则 `Slippage`。
5. `token.transferFrom(msg.sender, 0xdead, amount)`。
6. `quote.safeTransfer(to, 到手)`。
7. 发 `Redeemed`。

`previewRedeem`、`treasury`、`floorPrice` 用视图 `_afterSplit` 算拆分后的金库，`redeem` 用 `_splitQuote` 实际拆分；两者共用 `_partsOf` 和 `_quoteFor`，所以预览和执行一致（模糊测试逐次比对）。

### `work` 和 `previewWork`

- `work` 只做拆分（同分账模块 `GangSplitModule`）。
- `previewWork`：收款人还没被推送的部分（新入账里他们的份额，加上赎回留下的 `payeesPending`）达到分账模块的门槛时到期。没有收款人时永远不到期；封顶后只在 `payeesPending` 还没推完时可能到期。金库本身不需要 keeper。
- 两个边角：封顶后 `payeesPending` 低于门槛（尘埃级）时 keeper 永远不到期，由收款人自己调 `split`；报价币短缺时第一次 `work` 只记短缺，第二次才推送。
- `release` 开头的拆分如果已经顺带付清了这个槽的欠款，会回滚 `NothingOwed` 并连带回滚那次推送（封顶模块相同）。CLI 先调 `split` 再 `release`。

## 5. 不变量

| # | 不变量 |
|---|---|
| I-1 | `paidTotal <= capAmount`；收款人累计收到的加上欠款不超过 `capAmount` |
| I-2 | 任意顺序的入账、拆分、赎回、`release`、`setPayee` 之后，`floorPrice` 不下降（`Shortfall` 除外；取整误差只对金库有利） |
| I-3 | 一次赎回付出的报价币不超过 `amount × 金库 ÷ 流通量` |
| I-4 | 赎回不会动用欠收款人的钱；`release` 不会动用金库 |
| I-5 | 把一次赎回拆成多次，到手总额不超过这些币**不收手续费时**的按比例份额 `amount × 金库 ÷ 流通量`；手续费为 0 时不超过一次赎回的到手额 |
| I-6 | `previewRedeem` 的结果与紧接着执行 `redeem` 的结果相同 |
| I-7 | 其他资产不会有任何一部分到收款人或赎回者手里 |
| I-8 | 初始化之后，上限、比例、手续费和份额不可改变 |
| I-9 | 收款人拒收、耗尽 gas 都不能阻止拆分；赎回不调用任何收款人。赎回只调用 pad（只读）、代币和报价币；代币转账内部会通知税处理合约同步分红份额，失败不影响转账 |

I-5 的说明：有手续费时，分两次赎回会比一次略多。第一次付的手续费留在金库，其中一小部分落在自己还没赎回的币上，和所有留下的持有人一样。多出来的部分，分两次时约为 `手续费率 × 自己占流通量的比例 ÷ 4`，无限细分的极限是 `÷ 2`，手续费 2%、持有 1% 的人最多多 0.01%，手续费 5% 时最多 0.025%，不构成套利。初稿写的“拆分不超过一次”是错的，由模糊测试发现。

I-2 的依据：赎回后 `金库' ÷ 流通量' = (T − a·T/S·(1−f)) ÷ (S − a) ≥ T/S`，`f = 0` 时取等号。

## 6. 可能的攻击和绕过

| 手法 | 结果 | 处理 |
|---|---|---|
| 闪电贷或闪电兑换借出大量代币来赎回 | 从池子拿币等于按池子价格买入并交买入税，只有市价低于底价时才有利可图，这正是预期中的套利 | 流通量不读池子储备（K-4），无需额外处理 |
| 在大额税到账前买入、到账后赎回 | 入账按比例抬高所有人的底价，买入者付的是市价，赚不到 | 无需处理 |
| 赎回路径的重入 | 报价币转账给 `to` 时回调 | `nonReentrant`，先转代币再付报价币 |
| 让模块绑定诱饵币，把真币的税引给诱饵币持有人 | 做不到。模块创建时就写死了代币地址（K-13），只有这个币的持有人能赎回 | 合约层面已堵死 |
| 再发一个币，也把税收接收地址填成这个模块 | 那个币的税进了本模块的金库，封顶前按比例先给收款人，其余进金库，等于送给本模块那个币的持有人（模块还没绑定时，这笔钱先停在模块里，见 §4）。那个币自己没有底价 | 对本模块的币只有好处。那个币的页面上 `module.token() != 这个币`，网站和 CLI 不展示底价并显示警告。这是一次确定的链上读取，不是推测 |
| 把税收接收地址填成别人的底价模块，对外谎称“有底价” | 同上一行 | 同上一行。它和“把税直接分给 dev”的币没有区别，后者现在就允许 |
| 自己写一个合约冒充底价模块：自己发币、把自己填成收款地址（创建者本人不需要上架），并实现 `moduleType()`、`token()`、`floorPrice()` | 合约层面拦不住 | 网站、索引、CLI 必须核对来源：`GangHandlerAdmin.moduleOf(module)` 等于底价模块工厂，才当作 `floor-v1`（审计 L-2）。这是上线的前置条件 |
| 发币时把分红比例设成 100%，税全部给持有人分红，模块一分钱收不到，却显示“已绑定底价模块” | `bind` 回滚 `NothingForRecipient` | 99% 这类接近 100% 的设置合约不拦，网站必须展示“税里进金库的比例”（审计 L-1） |
| dev 或大户大量赎回 | 按比例拿走自己那份，剩下的人每枚底价不变（有手续费时略升） | 预期行为 |
| 把赎回手续费设得很高，再宣传“有底价” | 实际能拿到的远低于展示的底价 | 上限见 D-1；网站展示扣除手续费后的到手价 |
| 把上限设得极高 | 等于税大部分给 dev，金库涨得很慢 | 合约不限制。网站展示具体金额、进度和金库余额 |

## 14. CLI（2026-11-11）

`skill/gang-cli`：`gang create … --floor [--redeem-fee] [--tax-cap … --tax-cap-share … --split …]` 和 `gang floor status / redeem / distribute / release / set-payee / bind`。版本号没有动，发版时再定。

### 和 §8 的对应

- **先算地址再克隆**：发射的第一步上传元数据、算出代币地址，为它克隆模块，把地址、salt、元数据和税率记在本地计划里。之后的建币用同一个 salt 和元数据，不再读 `--logo` / `--description` 等参数。
- **建币前三道核对**：本地按计划的 salt 重算地址；不一致就拒绝；再向 pad 模拟 `createWithSalt`，返回地址和计划的不一致也拒绝。
- **不能手写**：`--recipient` 填的是底价模块时直接拒绝，提示改用 `--floor`。判断只凭链上记录，节点没答清楚就不建币，见下面“手写收款地址的检查”。
- **建币没发出时**：重建同一笔建币，不提示 `--restart`（那会为另一个地址再克隆一个模块）。
- **来源核对**：只有 `GangHandlerAdmin.moduleOf(module)` 等于底价模块工厂、且模块是为这个币克隆的，才显示金库和每枚底价；否则只显示警告，不生成任何 `gang floor` 调用。节点读取失败时提示重试，不说成“不是工厂创建的”。
- **进金库的比例**：克隆预览和 `gang info` 都显示封顶前后进金库的成交额比例。
- **赎回预览**：显示同样的代币在池子里卖出能拿多少，卖出更多时给出警告；池子价格读不到时也给警告。默认最低到手额就是预览值。
- **bond**：对 dev 的 GangBond 和喊单 bond，赎回按卖出处理，会破坏 bond 的赎回被拒绝，除非 `--break-bond` / `--break-call-bond`。
- **`gang tx`**：`Split(uint256,uint256,uint256)` 是回购、加池、推广池、底价四种模块共用的事件签名，字段含义各不相同。解码前先读发出事件的模块的 `moduleType()`；读不到时用中性字段名并标 `kindUnread`。

### 手写收款地址的检查

建币时 `--recipient` 不是创建者本人、也不是底价发射自己的模块时，CLI 判断它是不是底价模块（`typedFloorModule`）。原则：只凭链上记录说“不是”，节点没答清楚的一律不建币。

1. 所有读取钉在同一个区块上。节点没有这个区块只能报错，不能用旧状态回答“没有代码”或“没上架”。
2. 会回答“不是”的读取（登记表、代码、类型）直接取节点的原始结果，只有十六进制字符串才算答案；`null`、空串、缺结果都算节点没答。
3. 税处理合约的白名单里查不到：拒绝。pad 本来就只接受上架的非创建者收款地址。
4. 底价模块工厂自己的管理员合约（工厂里写死的地址）记着它：是底价模块。税处理合约以后换了主人也不影响。
5. 其他工厂上架的：平台模块，必须报出合法的类型名。报 `floor-v1` 的是底价模块；报别的类型的不是；答不出或答的不是类型名，按节点没答处理。
6. 平台手工上架的：这个区块上没有代码的是钱包；合约读一次类型，报 `floor-v1` 的是底价模块，其他回答、空返回、合约回滚都算“不是”。回滚要错误码、报错信息和附带数据都对得上才算合约自己的回滚。

已知并接受的取舍：手工上架的合约里，对未知函数返回 1–31 字节的、回退函数触发无效指令或耗尽 gas 的、回滚数据只有 1–3 字节的，会一直得到“无法确认”。这几种极少见，偏向安全一侧。

剩下的风险只来自一个伪造出格式完全正确的链上应答的节点；节点报错、落后或不回答都不会导致放行。
