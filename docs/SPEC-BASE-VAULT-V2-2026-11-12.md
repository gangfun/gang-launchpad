# 规格草稿 · 底仓金库（`base-v1`，毕业到 Pancake V2）

- 日期：2026-11-12 起草，同日第三版，并按第三版的独立评审修订（§13）
- 状态：**草稿，未实现，未审计**。第三版的评审没有发现严重或高危的机制问题；修订后的文本没有再评审。`createWithBase` 和底仓买入没有原型
- 背景：`docs/SPEC-PCS3-GRAD-BASE-2026-11-11.md` 和 `docs/SPEC-PCS3-GRAD-PHASE1-2026-11-11.md`（毕业到 Pancake V3 的方案，已搁置）
- 基础：GangLaunchpad 3.0 的曲线币（`kindOf = 1`），毕业路径不变

## 1. 做什么

给 3.0 的曲线币加一个发币时的选项，创建时写死：

1. **创建时买入底仓**：创建代币的同一笔交易里，用创建人付的 BNB 在曲线上买入总量的 5% 或 10%，放进这个币专属的金库合约。它是这个币的第一笔买入，狙击手排不到前面。
2. **毕业前锁住**：金库没有任何交易函数，也从不给任何人授权。
3. **毕业后线性释放**：毕业后第一次有人调用金库时开始计时，底仓在创建时选定的释放期里匀速释放到创建人的钱包（5% 的底仓可选 30、90 或 180 天，10% 的只能选 90 或 180 天）。释放出来的币是创建人的，怎么处置由他自己决定。

对外可以这样说：**dev 在开盘时按曲线价买了一份底仓，锁在合约里；毕业之后按天匀速解锁，全程链上可查。**

对外不能说的：

- 不能说金库会「托底」「做市」「只在高位卖」。金库不卖币，也不买币。
- 不能说底仓不会被卖出。释放之后创建人可以随时卖。
- **不能把保证金徽章当成对底仓的约束**（§6）。

这个功能回答的是「dev 拿不到底部筹码」。「不会做市」由现有的税收模块承担（回购销毁、自动加池、底价赎回），和本功能互不依赖。

### 不做什么

- 金库不交易。没有均价、档位、回购、分账。
- 第一版只对 WBNB 计价的币开放，不支持带分红的币（§6）。
- 第一版不和金库模式、推广分成组合。
- 众筹（多人凑底仓）不在本文范围（§9）。

## 2. 数字

曲线的参数（`CurveLogic3`，毕业金额记为 g）：毕业价 P = g ÷ 2 亿，是开盘价的 16 倍。

**创建人为底仓付多少**（含 1% 手续费，按库里的整数算法算出，只取决于毕业档位和底仓比例）：

| 毕业档位 | 5% 底仓 | 10% 底仓 |
|---|---|---|
| 6 BNB | 0.0994 BNB | 0.2090 BNB |
| 9 BNB | 0.1490 BNB | 0.3135 BNB |
| 12 BNB | 0.1987 BNB | 0.4180 BNB |
| 15 BNB | 0.2484 BNB | 0.5225 BNB |

- 手续费里有 70% 记回给创建人，可以用 `claimCreatorFee` 取，所以创建人在这一笔上实际付的手续费是 0.3%。
- 底仓的平均成本约为毕业价的 1/15（5%）和 1/14.5（10%）。毕业时按毕业价算，5% 的底仓值 0.25 g，10% 值 0.5 g。
- 底仓最多 1 亿枚，曲线上一共 8 亿枚，所以这一笔不会触发毕业。

**对别人的影响**：

- 底仓相当于毕业时池子里全部代币的 25%（5% 底仓）或 50%（10% 底仓）。
- 曲线的起始价格高出 1.10 倍或 1.22 倍；其他买家把币买到毕业，平均价格高 4.9% 或 10.3%。
- 创建人自己的钱包还可以在曲线上再买 1%。

**创建人能拿到多少**（g = 9 BNB）：

| | 5% 底仓 | 10% 底仓 |
|---|---|---|
| 最少：释放多少卖多少，期间没有任何别的买盘 | 约 1.8 BNB，价格最后是毕业价的 64% | 约 3.0 BNB，价格最后是毕业价的 44% |
| 价格一直维持在毕业价 | 2.25 BNB | 4.5 BNB |
| 价格更高 | 更多，没有上限 | 更多，没有上限 |
| 按毕业价卖出，几天收回全部成本 | 约 2 / 6 / 12 天（30 / 90 / 180 天释放期） | 约 6 / 12 天（90 / 180 天释放期） |
| 每天释放量占池子代币的比例 | 0.83% / 0.28% / 0.14%（30 / 90 / 180 天） | 0.56% / 0.28%（90 / 180 天） |

第一行是对持币人最坏的价格情形，同时是创建人最少能拿到的数，不是上限。收回成本之后，创建人在这份底仓上没有任何风险。这张表要出现在 CLI 的预览和代币页上。

## 3. 关键决定

| # | 决定 | 理由 |
|---|---|---|
| B1 | 每个币一个金库（克隆），不可升级，没有 owner | 和现有模块的做法一致 |
| B2 | pad 只增加一个创建入口和一个内部的「底仓买入」，不改交易路径 | 金库自己没有交易函数，也从不授权，毕业前它的币动不了（三轮评审都逐条核对过 pad 的转账路径） |
| B3 | **金库只做一件事：按时间把币转给创建人** | §13。让合约替 dev 卖币的两版设计都没有通过评审，问题出在思路上 |
| B4 | 释放从「毕业后第一次有人调用 `release`」开始计时，之后匀速 | pad 在毕业时不回调任何合约。任何人都可以调，晚调只会让创建人自己吃亏 |
| B5 | 收款人固定是创建人，不能改 | 合约最简单；钱包丢了是创建人自己的风险 |
| B6 | 释放期在创建时写死，之后谁也改不了 | 持币人要能在买入前看到全部规则 |
| B7 | 金库由模块直接克隆并在同一笔调用里初始化，不设工厂 | 新金库是一个没有私钥、此前没有代码的地址，不需要一串地址核对，也没有「工厂被换掉」的问题 |
| B8 | 金库判断「是否已毕业」读代币自己的 `locked()`，不读 pad | 金库不可升级，而 pad 可以升级。代币的这个状态只在毕业时改一次，之后代币没有管理员 |

## 4. pad 的改动

### 4.1 存储

新的 ERC-7201 命名空间 `gang.pad3.base`（内部库 `Pad3BaseStore`），只追加成员，槽位用测试钉住：

```solidity
struct Layout {
    address vaultImpl;                              // 金库的实现合约；0 = 不开放
    mapping(address token => address) vaultOf;      // 这个币的底仓金库，写入后不变
    mapping(address token => uint256) baseOf;       // 创建时买入的数量
}
```

实现合约和模块的顺序布局、7 个依赖地址、`TOKEN_VERSION`、`INIT_VERSION` 都不变。带底仓的币规则版本号仍是 1（发币选项不改版本号），但「曲线上没有人持有超过 1%」对它不成立；链下读规则时要同时读 `baseVaultOf`。

### 4.2 新增接口（放在 `Pad3Module`）

```solidity
struct BaseConfig {
    uint16 baseBps;    // 500 / 1000
    uint32 vestDays;   // 5%：30 / 90 / 180；10%：90 / 180
}

event BaseVaultImplSet(address indexed impl);
event BaseCreated(address indexed token, address indexed vault, uint256 tokens, uint256 cost,
                  uint16 baseBps, uint32 vestDays);

error BaseNotOpen();
error BadBaseConfig();
error WrongBaseVaultImpl();

/// owner。可以再次设置，只影响之后创建的币。传 0 = 停止。
/// 非 0 时要求 impl.pad() == 本 pad 且 impl.moduleType() == "base-v1"。
function setBaseVaultImpl(address impl) external;

/// 任何 Agent（规则同 create），nonReentrant，payable。只支持 WBNB 计价。
/// 不接受带分红的税配置（dividendBps 必须是 0）。
/// msg.value 必须正好等于 previewBaseCost(gradBnb, base.baseBps)，否则回滚 BadMsgValue。
function createWithBase(
    string calldata name, string calldata symbol, string calldata logoURI, string calldata metaURI,
    TaxConfig calldata tax, uint256 gradBnb, BaseConfig calldata base
) external payable returns (address token);

function baseVaultImpl() external view returns (address);
function baseVaultOf(address token) external view returns (address);
function baseOf(address token) external view returns (uint256);
/// 创建并买入 baseBps 的底仓要花多少 BNB（含手续费）。只取决于两个参数，任何人都改变不了。
function previewBaseCost(uint256 gradBnb, uint16 baseBps) external view returns (uint256);
```

**花费只有一个算式。** 在 `CurveLogic3` 里加一个 `internal pure baseCost(gradAmt, tokens)`，创建入口和 `previewBaseCost` 都用它，底仓买入时再算一遍并核对：

- `净额 = 按曲线买入 tokens 需要的计价币`（现有的 `_quoteInFor`，虚拟计价币 = `gradAmt ÷ 3`，已售 = 0）；
- `总花费 = ceil(净额 × 10000 ÷ 9900)`；
- `手续费 = 总花费 × 1%`；记进曲线的是 `总花费 − 手续费`（在全部 8 种组合里都比「净额」多 1 wei，照记）。

WBNB 计价时毕业金额就是 `gradBnb` 本身，所以花费是 `(gradBnb, baseBps)` 的纯函数，§2 的表就是它的全部取值。

`createWithBase` 的步骤：

1. `vaultImpl` 是 0 回滚 `BaseNotOpen`；`BaseConfig` 不合规或税配置带分红回滚 `BadBaseConfig`；`msg.value != baseCost` 回滚 `BadMsgValue`。
2. 按现有流程创建代币和曲线（`_createCurve`，计价币传 0 即 WBNB，参考池传 0）。
3. 把收到的 BNB 全部换成 WBNB（模块里已有 `_payIn`，`buyWithPromoter` 就是这样收款的）。因为要求正好相等，不存在多付和退款。
4. 克隆金库并在同一笔调用里初始化：`vault = Clones.clone(vaultImpl)`，`vault.initialize(token, 创建人, vestDays)`。
5. 写入 `vaultOf[token]`、`baseOf[token]`，发 `BaseCreated`（在买入的事件之前发，索引方先知道这个地址是底仓金库）。
6. **底仓买入**（库里的新入口 `CurveLogic3.buyBase`，要求这条曲线还没有任何成交）：
   - 不检查 Agent 门槛，不受 1% 钱包上限限制，不处理推广分成。
   - 更新 `realQuote` 和 `sold`；代币从 pad 直接转给金库；手续费照常 70% 记给创建人、30% 进平台费桶（用的是第 3 步刚换好的 WBNB）。
   - 事件的取值写死，和现有买入一致：
     - `Buy(token, vault, 总花费 − 手续费, 手续费, 0, tokens, realQuote)`
     - `TradeV1(token, vault, true, 总花费, tokens, 手续费, 手续费 × 70%, 价格, realQuote, tokens)`
   - 最省事的实现是复用现有的 `_execBuy`，按「已预付、无退款」调用。

说明：

- **abcd**：没开启 abcd 时直接调用 `createWithBase`；开启之后只能经 `createWithSalt` 调用。两条路径都要支持，CLI 按 `vanityDeployer()` 是否为 0 来选。经 `createWithSalt` 调用需要两处改动：
  - 它的入口白名单加上本函数的选择器；
  - **`createWithSalt` 改成可以收 BNB**（它现在不能收，`Pad3Module.sol` 第 222 行）。三轮评审都核对过：里面是 delegatecall，会带着 BNB 进去；白名单里另外六个入口都不收 BNB，遇到 BNB 会让整笔交易回滚，不会有 BNB 留在 pad 里；它是唯一的自我 delegatecall，有 `active` 标记，BNB 不会被花两次；回滚时 abcd 的临时状态一起回退。
- 创建过程中不运行任何外部人的代码：计价币是 WBNB，金库是刚克隆出来的。所有创建和交易入口都有重入锁。
- 金库的地址是可以提前算出来的（代理合约的下一个部署地址）。评审没有找到这能造成什么后果：router、聚合器、金库模式的登记都要求地址上有代码，pad 里按钱包记的状态又都以代币地址为键，而代币此时还不存在。
- 现有的 `create*` 入口不变，那些币没有底仓。

### 4.3 对交易的影响

- 金库的币在毕业前动不了：卖出、代卖、两个入口卖出、金库模式的锁仓和释放、打新的回收、推广分成的路径，每一条都需要金库先授权或者主动调用，而它两样都不会做。
- 底仓计入 `sold`，曲线的价格从底仓买入之后的位置开始。`getTokenInfo`、`tryBuy`、注册表的报价都读存储，自动反映底仓。对金库地址本身，钱包余量和买入报价都是 0。
- 评审用库里的整数算法验算了全部 8 种组合（4 个毕业档位 × 2 档底仓）：记进曲线的金额能买到的代币不少于底仓；曲线的乘积不变小；毕业时卖出的总量正好是 8 亿枚、池子拿到 2 亿枚，和没有底仓时一样；其他持币人全部卖出之后，曲线里剩下的钱等于底仓的净成本。金库锁住的币不会削弱曲线的偿付能力。
- 实现合约的源码不需要改（只有一处注释要提到 `baseVaultOf`）。`CurveLogic3` 多一个入口，实现合约和 `Pad3Module` 因为链接的库地址变了都要重新部署。
- 合约大小（磁盘上的构建产物）：实现合约 21,784 B，`Pad3Module` 14,337 B，`CurveLogic3` 13,905 B。评审估计模块增加 2.5–3.5 KB、库增加约 1 KB，都在上限以内。改完以构建结果为准。

## 5. `GangBaseVault`

每个币一个克隆。不可升级，没有 owner。

### 5.1 接口

```solidity
event Initialized(address indexed token, address indexed creator, uint32 vestDays);
event Began(uint64 startAt, uint256 total);
event Released(address indexed creator, uint256 amount, uint256 releasedTotal);

error NotPad();
error AlreadyInitialized();
error NotGraduated();
error NothingToRelease();

/// 只有 pad（实现合约里写死的不可变量），创建克隆的同一笔调用里调一次。
function initialize(address token, address creator, uint32 vestDays) external;

/// 任何人。
/// 还没开始时：要求代币已解锁（已毕业），记下开始时间和金库此刻的余额作为总量，返回 0。
/// 已经开始时：把到现在为止已经释放、还没转出的部分转给创建人。
function release() external returns (uint256 amount);

function pad() external view returns (address);
function token() external view returns (address);
function creator() external view returns (address);
function startAt() external view returns (uint64);     // 0 = 还没开始
function duration() external view returns (uint64);
function total() external view returns (uint256);
function released() external view returns (uint256);
function releasable() external view returns (uint256);
function moduleType() external pure returns (bytes32);  // "base-v1"
```

没有的东西：没有交易函数；不持有也不处理计价币；不给任何人授权；没有改释放期或收款地址的函数；没有提前释放、暂停、取消的函数。

### 5.2 规则

- **开始**：第一次调用 `release` 时，如果 `token.locked()` 已经是 `false`，记 `startAt = 现在`、`total = 金库此刻的代币余额`。代币还锁着就回滚 `NotGraduated`。
- **释放期内**：累计可释放的数量是 `total × 已过时间 ÷ duration`（向下取整）。`release` 转出「累计可释放 − 已转出」；为 0 时回滚 `NothingToRelease`。
- **释放期结束后**：`release` 把金库的余额全部转出，包括开始之后别人送进来的币。
- 毕业到第一次调用之间的时间不计入释放。创建人自己或者 keeper 在毕业后调一次即可；晚调只会让创建人自己晚拿到币。
- **永远不毕业**：底仓永远锁在金库里；创建人为它付的钱留在曲线里，没有退款或取消的途径。CLI 的预览里要写明。

### 5.3 不变量

- V1：释放期内，已转出的数量 ≤ `total × 已过时间 ÷ duration`。释放期结束后，已转出的数量等于金库收到过的全部代币（可以超过 `total`）。
- V2：释放期内，金库的代币余额 ≥ `total −` 已转出的数量。
- V3：代币只会从金库去创建人。
- V4：开始只会发生一次，而且只能在代币解锁之后。
- V5：毕业之前，金库的余额始终等于 `baseOf`。

## 6. 和现有功能的关系

| 功能 | 情况 |
|---|---|
| 带税的币 | 可以用。金库转给创建人不经过池子，不交税，也不会触发税处理器的任何调用。**注意**：带底仓的币不能带分红，所以带税时一定有一个税的收款人，通常就是创建人自己。创建人在池子里卖出时交的税，除了平台的 0.5% 之外会回到他自己手里。预览里显示的预计所得要按这个算 |
| 带分红的币 | **第一版不支持。** 分红份额等于持有人的余额，毕业后只要金库发生一次转账（包括别人转给它 1 wei），它就按全部持仓拿到份额，还没释放的底仓会分走持币人的分红 |
| **保证金徽章** | **保证金约束不了底仓。** GangBond 只检查「创建人钱包里的余额不低于他承诺的数量」，而金库一直在往这个钱包里补币。评审实测：创建人承诺持有 1%、缴 0.05 BNB，然后把 10% 的底仓每天释放多少卖多少，30 天卖完，保证金始终没有违约，最后按「已履约」结算；承诺的数量可以远小于他实际会拿到的底仓。另外保证金最长 90 天，盖不住 180 天的释放期；缴纳时承诺的数量不能超过钱包里已有的，所以还没释放的部分也没法提前承诺。GangBond 不可升级，这些改不了。所以：带底仓的币，页面不能直接显示现有的徽章和覆盖率，见 §10 |
| 封顶模块 | 互不影响，但封顶的承诺只管税，不管创建人的底仓。页面上两者放在一起显示 |
| 其他税收模块、喊单区 | 不受影响 |
| 推广分成、金库模式 | 第一版不组合 |
| 钱包上限 | 金库不受 1% 限制；创建人自己的钱包还能在曲线上买 1% |
| 聚合器、GangRouter、毕业路径、已有的币 | 不变 |

## 7. 安全检查清单

| # | 风险 | 处理 |
|---|---|---|
| R1 | 毕业前有人让金库的币动起来 | 金库不授权、不主动调用；pad 的每条转账路径都核对过 |
| R2 | 底仓买入绕过了 Agent 门槛和钱包上限 | 只有 `createWithBase` 这一条路径；数量只能是两档之一；买家只能是刚克隆出来的金库 |
| R3 | 金库的实现合约被设错 | `setBaseVaultImpl` 检查 `impl.pad()` 和 `impl.moduleType()`；只影响新币；每次更换走脚本，核对代码和本次构建逐字节一致，并在 fork 上创建、毕业、释放一遍 |
| R4 | 有人抢先调 `release` 让释放开始 | 无害。只能在毕业之后，效果和创建人自己调一样 |
| R5 | 有人往金库里送币 | 毕业前送不进来（代币锁着）。开始之前送的算进总量；开始之后送的在释放期结束时一并转出。既不会加快释放，也不会卡住 |
| R6 | 创建人的钱包丢了或被盗 | 收款地址不能改，币照常释放到创建人的地址。创建人自己的风险，CLI 里提示。另外创建人可以是一个持有 Agent 身份的合约，「不能改」固定的是地址，不是控制它的人 |
| R7 | 重入 | 金库只和代币合约打交道，先记账后转账；加重入锁 |
| R8 | 创建人用很少的钱拿到底仓，释放后卖出 | 这是这个功能的本意。持币人的保护只有两样：释放节奏写死并公开；§2 的表显示在预览和代币页上。**保证金不算保护**（§6） |
| R9 | 代币永远不毕业 | 底仓和创建人付的钱都永远锁着，没有退路。写进预览 |
| R10 | pad 升级改动了金库依赖的接口 | 金库只在初始化时被 pad 调用一次，之后只读代币自己的 `locked()`，不依赖 pad 的任何查询 |

## 8. 部署和升级

1. 部署金库的实现合约（构造时写死 pad 的地址）。
2. 构建新的 `Pad3Module`、`CurveLogic3` 和实现合约，7 个依赖地址不变。构建脚本每次都会连带部署一个新地址的 `Pad3FlyModule`（代码不变）。
3. **基线**：主网上现在的实现和模块比 abcd 那一版代码还早（`vanityDeployer()` 和 `createWithSalt` 在线上都会回滚）。本次升级要建立在 abcd 那一版之上。abcd 开不开启都可以上线底仓。
4. Safe 批次：升级 →（如果同一批里开启 abcd：`enableVanity`）→ `setBaseVaultImpl(impl)`。
5. 升级脚本：
   - `setBaseVaultImpl` 放在设置对比之后执行，否则会触发「设置变了」的检查；
   - 设置快照加 `baseVaultImpl()`（升级前读不到按 0 处理）；
   - 抽样只取最新的 25 个币，pad 又没法枚举带底仓的币，所以要像推广分成那样给一份探针名单（从 `BaseCreated` 事件里取），比对 `baseVaultOf`、`baseOf`；
   - `Pad3BaseStore.SLOT` 和成员位置；金库实现合约的代码和本次构建逐字节一致。

## 9. 众筹

不在本文范围。它需要另一次库和模块的改动：现在的代码里「创建人」和「调用者」是同一个（Agent 门槛、税收款人的判断、曲线记录里的创建人、`Created` 事件、abcd 的 salt、`claimCreatorFee`、保证金合约的缴纳人、推广分成的规则都用它），要分开得给 `CurveLogic3` 加一个带明确创建人参数的入口，并另外规定底仓买入手续费里记给创建人的那部分归谁。

## 10. 测试和链下

**测试**（本地跑，CI 不跑）：

- `createWithBase`：
  - 各项写入和事件的取值；8 种组合的花费和 §2 的表逐 wei 一致；`previewBaseCost` 和实际花费一致；
  - 金额不对回滚；每条路径前后 pad 的原生 BNB 余额不变；
  - 没开 abcd 时直接调用成功；开了之后直接调用回滚、经 `createWithSalt` 成功；经 `createWithSalt` 带 BNB 调用不收款的入口回滚；
  - 带分红的配置被拒；10% 配 30 天被拒；`vaultImpl` 为 0 时回滚；设错实现合约时 `setBaseVaultImpl` 回滚；
  - 平台费桶的收款用的是这一笔刚收到的钱；
  - 底仓买入之后曲线的买卖和毕业与没有底仓时一致；毕业金额不能被 3 整除的情况在库这一层用测试夹具覆盖。

- 对比：类型 1 的币（没有底仓）创建和毕业的行为和升级前相同；库头部注释里的「五处增加」改成六处；带底仓的币加进混合偿付能力测试和升级测试。
- 保证金：把评审的三个场景留作回归测试，同时作为页面逻辑的样例数据。

## 13. 设计历史和评审记录

- **V3 方案**（毕业到 Pancake V3）：三版设计、三轮评审，核心成立，但毕业前就存在一个买不了的池子，扫描工具和行情网站怎么显示没有查清。four.meme 在同类问题上被攻击后退回了 V2。已搁置。
- **本方案第一版**：金库在均价到过毕业价的 2 / 4 / 8 / 16 倍后分档解锁卖出。评审发现把价格拉高一秒钟就能永久解锁，而且解锁之后会一路卖到价位以下。
- **第二版**：改成只有现价和均价都在价位之上时才卖。评审发现创建人守在价位上买下金库卖出的每一块就能赚钱（卖出所得有一部分回到他手里），快速上涨之后金库会把价格卖回价位，回购和卖出会在回购线附近交替。
- **第三版（本文）**：这些问题来自「让合约替 dev 卖币」本身。改成金库只做线性释放。

**第三版的评审（2026-11-12）。** 两份独立评审，一份查金库和整体设计（`test/proto/ReviewV3_BaseVest.t.sol`，7 个测试），一份只读核对 pad 侧并用库里的整数算法重算了花费。两份都没有严重或高危的机制问题。

评审确认没有问题的：金库的币不能提前出来、不能去别的地址、不会卡住，释放速度不能被改变；别人送币既不加快释放也不卡住；带税的币释放时不扣税、不触发税处理器；毕业的同一个区块里可以开始；克隆和初始化是原子的；8 种组合下曲线的记账和毕业数量都自洽；`createWithSalt` 改成可收 BNB 之后不会有 BNB 滞留或被花两次；pad 的每条路径都动不了金库的币；合约大小有余量；主网上的模块确实早于 abcd；USDT、USDC 在主网按参考池定价（只开放 WBNB 的理由成立）。
